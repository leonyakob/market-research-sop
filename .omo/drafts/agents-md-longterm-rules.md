# Draft: AGENTS-md-longterm-rules

## Requirements (confirmed)
- 用户目标：生成正式工作计划，用于更新项目 `AGENTS.md`，但当前不直接修改原文件。
- 工作区策略：同一模块在 OpenCode 工作区只保留一个当前主文件，不保留 v1/v2/v3 多文件。
- 文件命名：SOP 主文件文件名不带版本号后缀。
- 版本保留：历史版本主要通过 Git / GitHub 提交记录 + 文档附录中的“版本历史”保留。
- Git 规则：每次对 `交付文档/` 下 SOP 主文件的有效内容修改完成后，必须执行 Git commit 并 push 到 GitHub。
- 回溯规则：恢复旧版本到当前主文件后，必须在该文件“版本历史”章节新增一条记录，并执行 Git commit 与 push。
- 行为规则：当用户要求“优化当前 SOP”时，不能立即修改，必须先澄清目标和范围，输出优化方案/修改计划，等待用户确认后再执行。
- commit message：不强制包含版本号，但必须包含模块名和变更摘要。
- 路径更新：规则中涉及的路径统一使用 `交付文档/SOP-融合与冲突处理规则.md` 与 `交付文档/SOP-通用模板.md`。
- 数据/资料规则：不取消区分，而是升级区分方式——按模块编号归类，并允许“双输入模块（数据+资料）”存在。
- 用户要求：先生成计划，经确认后，再派其他 agent 执行 AGENTS.md 修改。
- 高精度审查后新增：计划必须明确定义“有效内容修改”；必须把模块编号完整映射表作为明确交付物；必须把 push 失败、工作区有无关改动、双输入缺失、用户拒绝确认等异常边界写入候选规则。

## Technical Decisions
- 规则文件风格：保持结构化章节，但删去旧模式解释、重复描述、模糊词。
- 术语处理：移除“重要更新”等边界不清词汇，改为可执行条件。
- 输入分类方案：采用三分法——数据优先 / 资料优先 / 数据+资料双输入。
- 规划范围：不仅包括 AGENTS.md 文案改写，还包括相关路径、引用、分类映射、验证标准与执行顺序。
- 强化方向：把原本“提及即可”的边界情况升级为“候选 AGENTS.md 必须显式落地”的规则。

## Research Findings
- `AGENTS.md` 当前仍保留旧的多版本文件规则，与目标长期策略冲突。
- `交付文档/1-品牌策划全案SOP框架.md` 提供完整模块编号体系（1.1-8.5），可作为输入分类的权威来源。
- OpenCode 官方规则文件建议：规则应简洁、明确、可执行，避免冗长、重复和冲突。
- Metis gap analysis 结论：需要显式锁定范围、明确 acceptance criteria、处理 restore / push 失败 / 双输入缺失等边界情况。
- 高精度审查结论：当前计划框架正确，但必须进一步硬化“有效内容修改定义”“完整映射表交付”“异常边界规则落地”三项。

## Scope Boundaries
- INCLUDE：更新 `AGENTS.md` 的长期规则设计；按模块编号定义“数据/资料/双输入”；校验路径与行为规则；形成可交付计划。
- EXCLUDE：当前会话内直接修改 `AGENTS.md`；批量改写全部 SOP 文件；引入新自动化脚本、CI、hook、配置架构。

## Open Questions
- 无阻塞问题。下一步是把高精度审查提出的三项强化要求直接补入计划并重新提交用户确认。
